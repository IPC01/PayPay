# M-Pesa C2B, B2C and Reversal

The platform uses only M-Pesa C2B Single Stage and B2C for payments.
All HTTP payment routes contact the configured M-Pesa environment. They ignore
mock headers and `MPESA_MOCK_MODE`; gateway mocks are available only to unit tests.
Using the sandbox host is an external sandbox request, not a local simulation.

## Configuration

Configure these variables in `server/.env`; never put credentials in the client.
All of them are required for live calls (there are no hardcoded fallbacks):

- `MPESA_API_HOST`: for example `api.sandbox.vm.co.mz`.
- `MPESA_API_KEY` and `MPESA_PUBLIC_KEY`: credentials supplied by M-Pesa.
- `MPESA_SERVICE_PROVIDER_CODE`: business shortcode supplied by M-Pesa.
- `MPESA_ORIGIN`: sent unchanged as the `Origin` header.
- `MPESA_C2B_PORT`: for example `18352`.
- `MPESA_B2C_PORT`: for example `18345`.
- `MPESA_REVERSAL_PORT`: for example `18354`.
- `MPESA_INITIATOR_IDENTIFIER` and `MPESA_SECURITY_CREDENTIAL`: supplied by Vodacom; required only for reversals.
- `MPESA_TIMEOUT_MS`: defaults to `120000`; the response only arrives after the customer answers the USSD PIN prompt.

Authentication does not call `/ipg/v1x/getSession/` (blocked by the M-Pesa WAF).
Each payment request sends a Bearer token: `MPESA_API_KEY` encrypted with
`MPESA_PUBLIC_KEY` (RSA PKCS#1, base64).
Requests also include `Content-Type: application/json` and the configured Origin.
An HTTP 4xx without `output_ResponseCode` is treated as a rejected (not executed) payment.

## Request mapping

| M-Pesa field | Platform value |
| --- | --- |
| `input_TransactionReference` | Supplied reference, or a generated 20-character reference starting with the wallet type's initial prefix (max 8 characters) |
| `input_CustomerMSISDN` | Phone normalized to `25884xxxxxxx` or `25885xxxxxxx` |
| `input_Amount` | Positive amount with up to two decimal places, sent as a string |
| `input_ThirdPartyReference` | Persisted transaction UUID without hyphens, uppercase (32 hex characters), unique in the platform; must match `output_ThirdPartyReference` |
| `input_ServiceProviderCode` | `MPESA_SERVICE_PROVIDER_CODE` |

The database enforces uniqueness of transaction references. A supplied reference
cannot be reused (HTTP 409); a missing reference is generated by the platform.

M-Pesa accepts only letters and digits in both references (hyphens are rejected with
INS-17/INS-19), and `input_TransactionReference` must have 1 to 20 characters.
Provider responses retain `output_ConversationID`, `output_TransactionID`,
`output_ResponseCode`, `output_ResponseDesc` (or `output_ResponseDescription`),
and the complete response JSON.

## C2B: receive money, without platform fees

- Authenticated client: `POST /api/payments/c2b` with a Bearer JWT.
- API key: `POST /api/v1/mpesa/c2b` with `x-api-key` and `transaction:c2b` scope.
- External resource: `/ipg/v1x/c2bPayment/singleStage/`.

```json
{
  "walletCode": "000005",
  "amount": 100,
  "phone": "258841234567",
  "reference": "INVOICE001"
}
```

`reference` is optional. The customer authorizes the USSD push on their phone.
The platform never requests or stores the M-Pesa PIN. Only an `INS-0` response
credits the full amount to the selected active M-Pesa/MZN wallet.

`POST /api/payments/direct` uses the same C2B gateway without a client wallet,
for example for subscriptions. It accepts `amount`, `phone`, optional `reference`
and `provider: "mpesa"`.
The old `/api/mpesa-service-test/c2b` URL is a compatibility alias to the same
real C2B implementation, not a separate test provider.

## B2C: withdraw money, with a fixed cost

- Client withdrawal: `POST /api/withdrawals` with a Bearer JWT.
- Compatible client route: `POST /api/payments/b2c` using `walletCode`.
- API key: `POST /api/v1/mpesa/b2c` with `x-api-key` and `transaction:b2c` scope.
- External resource: `/ipg/v1x/b2cPayment/`.

```json
{
  "walletId": "<wallet-uuid>",
  "amount": 100,
  "phone": "841234567",
  "note": "Withdrawal"
}
```

Every B2C route uses the same withdrawal implementation, approved-KYC check,
wallet permissions, minimum/maximum and fixed `withdrawalFeeAmount` setting.
The recipient receives the requested amount; the wallet reserves that amount
plus the fixed cost, with no percentage calculation.
For example, a 100 MZN withdrawal with a 10 MZN cost requires 110 MZN.
The reservation and ledger entry are committed under a wallet row lock before
contacting M-Pesa, preventing simultaneous withdrawals from spending the same funds.

The B2C form and withdrawal form are the same screen. Administrative approval
and rejection no longer execute or simulate transfers; the old action URLs return
HTTP 410. Historical requests are retained and are not automatically resubmitted.
The old `/api/emolar` payment alias has been removed.

## Reversal: full reversal of a successful transaction

`PUT https://<MPESA_API_HOST>:<MPESA_REVERSAL_PORT>/ipg/v1x/reversal/` with:

| M-Pesa field | Platform value |
|---|---|
| `input_TransactionID` | `providerTransactionId` (M-Pesa `output_TransactionID`) of the original transaction |
| `input_SecurityCredential` | `MPESA_SECURITY_CREDENTIAL` |
| `input_InitiatorIdentifier` | `MPESA_INITIATOR_IDENTIFIER` |
| `input_ThirdPartyReference` | Reversal transaction UUID without hyphens, uppercase |
| `input_ServiceProviderCode` | `MPESA_SERVICE_PROVIDER_CODE` |

`input_ReversalAmount` is never sent: only full reversals are supported.

- Client (wallet owner): `POST /api/transactions/{id}/reverse`.
- Administrator: `POST /api/admin/transactions/{id}/reverse`.

Only `success` C2B/B2C transactions linked to a wallet can be reversed, once.
A `reversal` transaction is created (`originalTransactionId` points to the original,
with its own unique reference). On success the original becomes `reversed`.

- C2B reversal: the amount is debited (reserved) from the wallet before calling M-Pesa;
  it is blocked if the balance is insufficient and refunded if M-Pesa rejects it.
- B2C reversal: on success only the withdrawn amount returns to the wallet;
  the fixed withdrawal cost is not refunded.

HTTP status codes follow the same rules as payments (200/202/400, 404, 409).
The sandbox accepts any initiator credentials and TransactionID, so validate them in production.

## Results and uncertain outcomes

- HTTP 200 (201 for a client withdrawal): `success: true`, confirmed `INS-0`.
- HTTP 400: rejected or not sent. A reserved B2C amount and its cost are refunded.
- HTTP 202: `success: false`, `pending: true`, `reference` and `transactionId`.
  No confirmed credit is applied to C2B. For B2C the reservation is retained.
- HTTP 409: a reference was already used.

Missing responses, network timeouts, uncertain provider codes and mismatched
third-party references must not be treated as proof of failure. The platform
does not retry a payment automatically or release an uncertain B2C reservation.
It also reports HTTP 202 if a received result could not be committed locally.

**Pending results require reconciliation with M-Pesa using the stored transaction
and provider references.** This change does not implement a callback or a status
query API: those contracts were not supplied. Never create another payment to
resolve an uncertain result. Old manual approval/rejection is not a reconciliation
mechanism and cannot release funds.

## Validation without real payments

From the server directory:

```powershell
node --test test\mpesa.test.js test\wallet-payments.test.js test\reversal.test.js
```

These tests stub the gateway, HTTP transport and database methods; they do not
send USSD pushes or transfer money. Real sandbox/live end-to-end validation
requires valid credentials, a configured business shortcode and authorized test numbers.

The importable examples are in [PayPay-MPesa.postman_collection.json](PayPay-MPesa.postman_collection.json).
The collection sends real external requests to the configured environment.
